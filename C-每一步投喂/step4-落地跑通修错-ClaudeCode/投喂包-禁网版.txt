【使用方式 · CC-Switch 专用 · 先读这段】

本文件用于**第一个终端**：模型 **GLM-5.3**，思考强度 **high**。
CC-Switch 的两个约束决定了工作方式：

- **换模型 = 重开终端 = 上下文丢失** → 所以不要为了"用更省的模型"中途切模型
- **切思考强度要等当前这轮生成完** → 所以同一终端内可以分轮调整档位，但不能中途打断

因此节奏是：
1. 本终端（GLM-5.3）先做完「阶段 A」→ 自己跑验证 → **commit**
2. 同一终端继续做「阶段 B」（生成完后把档位调成 xhigh）→ **commit**
3. **只有卡在某处连续 2 轮没解决**，才重开终端切 DeepSeek V4.1；
   新终端第一条消息直接粘 `接续上下文-换终端用.md` 并填好卡点

每完成一个可提交的单元就 `git commit` —— 重开终端后，`git log` 就是你唯一能继承的记忆。

### A0. 🔴 先修一处阻塞级桩代码（P0，不修则 host 根本启不起来）

`src/dsh-host.js` 的 `locateRuntime()` 目前是桩：

```js
const nodeExe = process.execPath        // ❌ 错：这是 Electron 可执行文件，不是外部 Node
let npxCli = '<占位 npx-cli.js 绝对路径>'  // ❌ 占位未实现
```

SPEC §6 明确要求：
- **禁止把 `process.execPath` 当 Node 用**（`ELECTRON_RUN_AS_NODE` 也不是可靠的"关闭开关"）
- 必须定位**外部 Node 安装**对应的 `node.exe` 与 `npx-cli.js`，并以**绝对路径**传入
- Windows 下不以 `shell:false` 直接跑 `npx.cmd`，也不拼 `cmd /c`
- 最终调用形态：`spawn(nodeExe, [npxCli, "--yes", "--offline",
  "--package=@deepseek-ai/dsh@0.1.7-alpha", "--", "dsh", "web", "--no-open"], options)`
- 定位失败要报 `E_RUNTIME_MISSING` / `E_CLI_MISSING` 并给出环境准备提示，不要静默继续

实现建议：查注册表 / `where node` / 常见安装目录（Program Files\nodejs、
`%APPDATA%\nvm`、fnm/volta 目录）拿到外部 `node.exe`，再由它反推 npm 安装根找 `npx-cli.js`；
拿到后**实际校验文件存在**再返回。

### A0-2 🔴 ESM 里用了 `require`（P0，运行时必崩）

`package.json` 是 `"type": "module"`，以下三处在 ESM 文件里调用 `require`，
运行到就会抛 `ReferenceError: require is not defined`：

| 文件:行 | 现状 | 应改成 |
|---|---|---|
| `src/main.js:334` | `const { dialog } = require('electron')`（在 `promptRetryOrExit` 里） | 顶部统一 `import { app, BrowserWindow, protocol, session, dialog } from 'electron'` |
| `src/ipc.js:133` | `require('electron').app` | 顶部 `import { app, ipcMain } from 'electron'` |
| `src/logger.js:40` | `require('electron-log')` | 顶部 `import electronLog from 'electron-log'` |

⚠ 例外：`src/preload.js` 里的 `require('electron')` **是对的**，它会由 esbuild 打成 CJS
（`build/preload.cjs`），**不要改它**。

这三处都只在**错误/降级路径**才执行（host 启动失败、日志初始化、app 引用），
所以编译期发现不了，真出问题时才炸 —— 必须提前修掉。

## 第三步：Phase 2.2 — 产出 `.github/workflows/release.yml`

按 SPEC.md 第 11 节"打包与发布"的配置，写一个 GitHub Actions：

```yaml
name: release
on:
  push:
    tags: ['v*']   # 推送 v0.1.0 触发
jobs:
  build:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - run: pnpm exec electron-builder --publish always
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      # 同步到腾讯云 COS
      - name: Sync to COS
        if: startsWith(github.ref, 'refs/tags/v')
        run: |
          # 用 coscmd 或 mc 客户端
          # secrets: COS_SECRET_ID / COS_SECRET_KEY / COS_BUCKET
          coscmd upload -r ./dist/${{ github.event.repository.name }}-Setup-${{ github.ref_name }}.exe \
            /dsh-desktop/v${{ github.ref_name }}/
        env:
          COS_SECRET_ID: ${{ secrets.COS_SECRET_ID }}
          COS_SECRET_KEY: ${{ secrets.COS_SECRET_KEY }}
```

确认 actions 能 dry-run 通过（用 `act` 工具本地测，或直接 push 到一个测试仓库看）。
