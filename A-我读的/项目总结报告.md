## 五、经验与方法论沉淀

### 5.1 制度性做法（最有价值的部分）

**① 三审制**
- 一审 = 验收面（SPEC §12 的 A01~A10）
- 二审 = 承诺面（散落在 §3~§10 的条款 —— **最容易欠账**）
- 三审 = 修复复核（实现方修完必须重新核）

**② 独立核验六手法**
1. 查第三方**源码**确认运行时行为（不猜）
2. grep 要覆盖等价写法（`86400000` vs `24*60*60*1000`）
3. 先做最小实验排除自己的环境干扰（`spawnSync`/`execFileSync` 返回 EBUSY）
4. **断言非空转验证**：把坏输入喂进去，必须被拒
5. 包内标志串核验（证明产物 == 源码）
6. 跨模型交叉（不同模型错误模式不同）

**③ 静默失效三形状**（今天抓到的所有问题都落在其中之一）
1. **声明了但从未接线**
2. **兜底/记录被静默吞掉**
3. **错误路径的代码从未执行过**

**④ 审计环境声明** —— 报测试失败前先证明"是我的环境"，并写进报告。

**⑤ 审计独立性护栏** —— 验收报告只由审计方写；实现方写入时必须**不改原文 + 追加独立性声明**。

### 5.2 新增的两条硬规则

> **R1：凡代码读取第三方运行时对象的字段，必须以该对象在真实运行时的形状核验。**
> 假件里的字段必须先证明"真实存在"才可用于验证。
> （教训：`processArguments` 在假件里存在、在真实 Electron 里不存在）

> **R2：凡遇"互斥 / 闩锁 / 守卫"结构，必须同时核它的解除路径。**
> 只有加、没有解 = 一次性开关。
> （教训：`inflight` 复位只在 `dispose()` 里）

### 5.3 一条通用心法

> **每当遇到一个"只有真实环境才暴露"的问题，就造一个本地能跑的子路径。**

本次实例：`release.mjs --plan-only` —— 把"CI 才能碰到的环节"变成"本地能验的环节"。这是防止这类问题复发的**根本手段**，比修那一个 bug 有价值得多。

### 5.4 协作层面

1. **思考强度按任务切换**：设计/判断类用 high，纯执行用 low/medium。构建类任务**明确写"失败只报告不硬修"**，防止模型在中等档位下乱改。
2. **变量分离**：不让我同时动两个高风险变量（如"首次发布 + 上游大版本跨越"）。
3. **上下文管理**：终端上下文到 98% 时，**新开终端 + 快照文件**（`-c` 恢复后上下文还是满的，不解决问题）。
4. **隐私边界前置**：把"禁止抓屏"写进项目硬约束，而不是事后补救。

```

③ node tools/release.mjs --plan-only   ← 本地先验，必须 EXIT=0
④ git tag v<版本> → push → CI
⑤ 发布后核：Release 产物 + COS 的 cn-stable.yml（404→200）
```

## 八、一句话总结

**这个项目真正的产出不是那个 80MB 的安装包，而是一套「不靠信任、靠证据」的验收方法。**

它让一个"mock 45/45 全绿"的项目，在装机第一天就崩、在 CI 第一次就红——然后把每一个问题都抓出来、修掉、登记、防回退。所有结论都指向一条可复现的证据，所有错误（包括我自己的）都写进了报告。
