# DeepSeek Harness Desktop —— 三份 AI 资源的效率最大化方案（补充视角）

> 目标：全新独立 Electron 壳（Windows），包住 `dsh web`，实现 **开机美化 / 自动检查更新 / 常驻托盘** 三大功能
> 资源：Claude Code + DeepSeek V4.1（API 计费）· WorkBuddy 国内版 3000 积分 · WorkBuddy 国际版 GPT-5~6 系列 440 积分

## 0. 一句话结论

**别把任务平均分给三个 AI。按「边际成本 × 出错代价」分工：最贵的 GPT 只写图纸和终审，中等的国内版批量砌砖，最便宜的 Claude Code 干「跑—报错—改」的无限循环。**

核心数据：如果让国内版去做调试循环（一次 30~80 积分 × 10~20 轮），会烧掉 1000~1600 积分；把同样的循环交给 Claude Code + DeepSeek V4.1（API 计费），国内版总消耗可以压到 **600 积分以内**，国际版压到 **180 积分以内**。

## 1. 三个资源的经济学定位

| 资源 | 模型 | 额度性质 | 单位成本 | 最强能力 | 最该干的活 | 绝对别干 |
|---|---|---|---|---|---|---|
| **Claude Code + DeepSeek V4.1** | DeepSeek V4.1 | API 计费，几乎不限次 | 极低（几分钱/次） | 直接读写文件、跑命令、读报错、循环修 | 编译/构建/试错/联调/跑安装包的**无限循环** | 架构设计（想不深，返工代价大） |
| **WorkBuddy 国内版** | 国产模型全家桶 | 3000 积分，按次消耗 | 中（~20~80 积分/次） | 批量产出、中文表达、多代理并行 | **按图纸批量生成代码**、写文档、生成资源 | 反复调试（烧积分最快的方式） |
| **WorkBuddy 国际版** | GPT-5 ~ GPT-6 系列 | 440 积分，**极稀缺** | 高（~40~80 积分/次深度） | 一次性想对、全局权衡、发现设计缺陷 | **写架构 spec**、关键卡点攻坚、**最终审计** | 写样板代码（用茅台浇花） |

### 三条铁律

1. **贵的模型不写代码，只写「图纸」和「判决书」。** GPT-6 一次深度会话 ≈ 60 积分，440 积分也就 7 次左右。它每多写一行样板代码，你就少一次救火机会。
2. **调试循环绝不能走按次计费的积分。** 编译报错 → 改 → 再报错，这个循环次数完全不可预测（10~30 轮很正常），必须放在 API 计费的 Claude Code 上。这是**整个方案里最省钱的一条**，没有之一。
3. **三个 AI 之间不靠聊天记录传递信息，靠 Git 仓库。** 它们没有共享上下文。唯一可靠的共享内存是磁盘上的文件：spec、代码、CHANGELOG。每个 AI 开工第一件事是读仓库，收工最后一件事是写仓库。

## 2. 方法论：Spec-Driven 瀑布式外包

三个 AI 各写各的必然合并不起来。**必须先冻结一份 spec 当唯一契约。**

```
   [国际版 GPT-6]                    ← 只做 2 次，产出纯文本
        │  架构 spec + 接口契约 + 验收清单
        ▼
   ┌─────────────────┐
   │  仓库 /SPEC.md  │  ← 三个 AI 的唯一真相源（SSOT）
   └─────────────────┘
        │                          │
        ▼                          ▼
 [国内版 批量砌砖]          [Claude Code + DS V4.1]
   按 spec 写模块代码          跑 build / 排错 / 联调
        │                          │
        └──────────► 代码落盘 ◄────┘
                        │
                        ▼
              [国际版 GPT-6 终审]   ← 第 3 次，挑设计缺陷
                        │
                        ▼
              打包 / 发布 / 文档
```

**为什么是瀑布而不是并行？** 因为这三个 AI 的上下文不互通。并行 = 三份互相冲突的代码 = 合并成本远高于串行。串行 + 冻结 spec，看似慢，实际总耗时最短。

## 5. 三个功能的实施要点

### 5.1 开机美化（已完成视觉层）

- 窗口：`frame:false, transparent:true, 600×360, center, skipTaskbar`
- 序列：显示 splash → spawn `dsh web` → 轮询 `127.0.0.1:3080` → 就绪后创建主窗口 → splash 淡出关闭
- **关键**：splash 必须比主窗口先出现，且不能阻塞主进程。轮询要有超时（建议 30s），超时后显示错误页而不是卡死
- 已交付 `src/splash.html`：内嵌 SVG 鲸鱼 + **品牌字逐线条书写动画**（约 3.7s，可调 `PEN_SPEED`）、
  状态文案可 IPC 更新、支持 `prefers-reduced-motion`、可独立双击预览（`?t=秒` 定格任意时刻）
- ⚠ **关闭时序尚未定案**（动画 3.7s vs host 可能 1.5s 就绪）—— 见 `B-AI共享/INTERFACE.md` §3 待决项 D2
- ⚠ 注意：早期文档里写的"流光进度条"已不存在，当前版本无进度条

### 5.2 常驻托盘

Windows 托盘的四个坑（务必写进 spec 让 GPT 审）：

| 坑 | 表现 | 规避 |
|---|---|---|
| 图标糊 | 16×16 拉伸成马赛克 | 提供真 16/20/24/32 帧（已交付） |
| 进程残留 | 关窗后 dsh 子进程还活着占着 3080 | `app.on('before-quit')` 里 kill 整个进程树 |
| 开机自启失效 | 打包后路径变了 | 用 `app.setLoginItemSettings`，且只在安装版启用 |
| 托盘图标丢失 | Explorer 重启后托盘图标消失 | 监听并重建 |

### 5.3 自动检查更新 ⚠️ 你选了 GitHub Releases —— 这里有个必须先解决的矛盾

**问题**：你在园区内网（10.35.44.27/21），且你的历史记录里 GitHub Pages 等境外服务默认不可用。`electron-updater` 走 GitHub Releases 时会请求 `api.github.com` 和 `objects.githubusercontent.com`——**大概率超时或直接失败**，表现为"永远检查不到更新"或"下载到 99% 卡死"。

**推荐解法：GitHub 做发布源，COS 做分发通道（双通道）**

```
GitHub Actions 构建
  ├─> 上传到 GitHub Releases（海外通道 + 版本归档）
  └─> 同步到腾讯云 COS ap-shanghai（国内通道）
            │
            ▼
   electron-updater 指向 COS generic provider
```

好处：发布流程仍以 GitHub Releases 为中心（符合你的选择），但国内用户实际从 COS 拉取，速度和可用性都有保障。同时保留了海外可用性。

**代码层面**（写进 spec）：
- 主 feed：`generic` → COS，带 `latest.yml`
- 失败重试 / 超时（建议 8s）后回落 GitHub provider
- **更新包必须校验 sha512**（electron-updater 默认做），COS 通道也不能省
- 提供"手动检查更新"入口（托盘菜单），并在 UI 上明确显示当前通道
